# Production and delivery runbook

The source list in Feishu determines topic, discipline, course and teaching requirements. `data/prompts.json` is the public final artifact record. The existing incremental state is a recovery journal, not another source for final titles or Prompts. Set `LEADDE_WORKSPACE` to the production workspace and `LEADDE_REPO` to the publishing checkout. Existing batch sizing, course priorities and source discovery remain in `sources.json` / `incremental_agent.py`.

1. Discover and deduplicate using existing source discovery. Preserve the existing Agent Key, Feishu record ID and knowledge ID after renaming. Link synonyms rather than adding another topic. `python3 scripts/automation/reserve_identity.py KEY` allocates an ID once before production and persists it in the work item; never calculate a replacement from a changed name. Keep `Name` as the original name and `Standard English Name` separately. Feishu `Review Decision=批准制作` approves a proposal, not its completed video.
2. Before storyboarding, verify the standard term against course scope, formulas and a real reference. Record terminology evidence and the original requirement. Reuse the existing course kit and batch rendering workflow. Do not start another batch for in-progress IDs.
3. Finalize the actual storyboards, inputs, tools, dependencies and source paths in `production`. Render and probe the final file. Update the public Prompt from the final scenes, never from an obsolete request. State tool, missing materials and whether exact reproduction was actually tested. `requirement_prompt`, `production` and `prompt` serve distinct purposes within the same record.
4. Review terminology, explanation, causal motion, text/formula/diagram consistency, stable frames and transitions, legibility at common player sizes, and matching media/cover/Prompt versions. Record actual reviewer, timestamp, checks and evidence. File existence, an overlap script or a boolean flag alone is insufficient. Existing unreviewed files remain unreviewed.
5. Persist a complete final record JSON and put its path in the work item's `artifacts.final_record`. `checkpoint KEY 待发布 --artifacts ... --review-passed` validates the record and identity. On revision, increment the artifact version, retain the ID and previous record/player in history, invalidate only version-specific publication state, and record pending Feishu, repository video, native player, cover, Prompt and package destinations.
6. `publish_ready.py KEY [--channel feishu|github|all]` validates the final record, then attempts channels independently. Successful channels are skipped for the same version. Save attachment tokens and GitHub attachment URL/comment identity immediately. Recover uncertain uploads by stable ID + artifact version before retrying. Do not create a new attachment Issue per item or retry; use an existing asset Issue and a version-specific comment. Never reuse an older attachment URL for new bytes.
7. GitHub catalog upsert matches stable ID / Feishu record ID. Preserve existing slugs and ID anchors. Generate pages via `scripts/build_github_readme.py`. Publish course packages with `scripts/publish_course_video_releases.py`; its inventory comparison skips unchanged versions and retains fixed tags/download filenames. `data/releases.json` records only successfully observed assets. Packaging failures do not block other courses.
8. Report channel errors and pending synchronization. A failed publisher never invokes a renderer. Do not mark end-to-end delivery complete while any required destination still refers to the previous version. Licenses and human approval must not be invented.

Local tests: `python3 -m unittest discover -s scripts/tests`; `python3 scripts/validate_catalog.py`; serve the existing static site over HTTP. These checks do not substitute for real external writeback/readback and playback evidence.
